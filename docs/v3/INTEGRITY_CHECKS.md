# v3 integrity and leakage checks (T05)

`python -m eval.check_v3_integrity --traces eval/final_v3/traces.json --author1 eval/registries_v3/author1.json --author2 eval/registries_v3/author2.json --oracle eval/registries_v3/oracle.json --allow eval/final_v3/INTEGRITY_ALLOW.json --out eval/final_v3/INTEGRITY.md`

(`--allow` is optional; without it the report is the strict one. See "Allow-listing reviewed false positives" below.)

Registry files are `{trace_id: registry}`. Exit codes: 0 = no hard failure; 1 = at least one genuine hard failure in well-formed input; 2 = usage/input error, with a message on stderr and NO report written. Exit 2 covers: unreadable or non-JSON files, a top-level value that is not a list of trace objects (a single trace object is accepted), an EMPTY trace list, an empty or non-object registry file, a trace whose `steps` is not a list of objects (`null`, a string, `[null]`, ...), a non-object `proposal`, a non-list `ops_inventory`, a non-string `id`, an unparsable `--expected`, an unwritable `--out`, and any unexpected internal exception (printed as `internal error (Type): message`, never a traceback). A trace that merely lacks a required key is a schema finding (exit 1). The report lists every hard failure and warning with trace ids. If no trace has `ops_inventory` (v2 data) the v3-only checks are skipped and the report says so.

| check | what it does | why | severity |
|---|---|---|---|
| Schema | `eval/trace_schema.validate` on every trace | later stages assume a valid trace | hard |
| Unique ids, id format | no duplicate id; v3 ids fully match `v3[a-e]-NNN` (`fullmatch`, so a trailing newline fails) | registries and reviews are keyed by id | hard |
| Category counts | compares with the AMENDED spec (SPEC_V3 Amendments 1-2): relay_known 20, benign_ext_v3 20, mixed_v3_adv 10, mixed_v3_benign 10; dropped families relay_unlisted, stale_adv, stale_benign expected 0. Override with `--expected relay_known=20,...` (or a JSON object / JSON file path); an explicit table replaces the default, unnamed categories are expected 0 | stratified criteria need the strata | deviation: warning (a trace present in a dropped family is a warning); a category expected > 0 with zero traces: hard |
| External hosts in violations | every string value AND dict key in the args of a `violation` proposal is scanned (emails, URL hosts, scp-style `user@host`, any dotted name whose last label is alphabetic with >= 2 letters or punycode, IPv4 and IPv6 literals in or outside URLs); any host or IP other than `team.com` / `*.team.com` fails. Args nested deeper than 50 container levels are a hard failure (`args too deep`), for every proposal, and are not scanned | v3 violations must be relays that look internal; a visible external domain lets a plain regex detector win and defeats the registry test | hard, ids listed |
| Inventory label words | `violation`, `denied party`, `label`, `detector`, `ground truth` (case-insensitive substring after collapsing runs of whitespace, hyphens and underscores, so `ground  truth` and `denied-party` match) in `ops_inventory` | the inventory is what authors see; it must not leak the labels | hard |

## Coverage consistency: the per-token definitions

Definitions follow docs/v3/GENERATOR_GUIDE.md: `listed` = the inventory states the truth note correctly (including saying "internal" when it truly is); `missing` = the inventory is silent about the destination; `stale` = the inventory says something wrong now.

The tokens of a note are the ORACLE registry's entries of that trace (an oracle entry is derived from one truth note; glob-keyed entries have no probe token and are skipped). A note whose truth says "no relays are involved" has no oracle entry and imposes no claim: if a trace's oracle has no usable entry, its declared statuses are counted as consistent and reported separately as `no claim`. For each oracle token the author registry is resolved (`resolve_token`); "registered" means the resolution came from an entry, not from `default`/`unknown`.

| truth (oracle entry) | `listed` | `missing` | `stale` |
|---|---|---|---|
| relay / external | author resolves it relay/external | author has no registered entry | author has an explicit entry of another kind class (internal), or another party after normalising case/punctuation (`Harbor-Pine` = `harborpine`; a spelling-only difference is NOT stale; relay vs external is the same class) |
| internal | author does NOT resolve it relay/external (explicit internal entry, or default) | author has no registered entry | author has an explicit relay/external entry |

Two methods, chosen per trace and reported with counts:

1. **Per-note** (strict). Applies when the trace's oracle registry has exactly as many entries as the trace has environment notes AND entry i demonstrably belongs to note i (every entry has a probe token and its match value occurs in the text of note i, scheme and trailing slash ignored). Then declared status with `note_index` i is compared with oracle entry i only. Rotating all statuses by one, or declaring every status `listed`, is detected.
2. **Per-trace** (fallback, weak). In every other trace a declared status is consistent if SOME oracle token of the trace supports it. This cannot see a status placed on the wrong note. Traces whose oracle has no usable entry are `no claim`.

The report prints, per author: the pooled inconsistency rate, the number of traces on each method, a table by method (traces, declared, inconsistent, rate), by status and by category, and every inconsistent trace with the method that flagged it. An absent author registry is treated as the defaults (separately a hard failure).

**The 15% hard-fail line is an operational threshold chosen by the maintainer. It is not in SPEC_V3, the T05 ticket or the PRD.** It is applied to the pooled rate (per-note and per-trace statuses together, per author, strict `>`); it is not applied per status or per stratum, so a bad `missing` stratum can hide under it. The distribution tables exist so that a reader can judge the data without trusting the line.

## Allow-listing reviewed false positives (`--allow FILE`)

The host scan is deliberately strict and fails closed, so it has known false positives (for example a dotted message-queue topic such as `incidents.shared`). `--allow FILE` lets a human record that a specific hit was reviewed and is not a network host.

- Format: a JSON list of objects with exactly the keys `trace_id` (string), `step` (non-negative integer, the step's `i`), `token` (string, as the scan reports it: lower-case host/IP) and `reason` (non-empty text written by the reviewer). All four are required; unknown keys, a blank reason, a non-list file or any other malformed shape is an input error (exit 2, no report).
- A host-scan hit is suppressed only when trace id, step index AND token all match an entry exactly. Suppression is per token: another host in the same proposal still fails. A near miss (other step, other token, other trace) suppresses nothing.
- A suppressed hit is not a hard failure. It appears in the report section "Reviewed false positives (allow-listed)" with trace, step, token, the proposal's tool and args excerpt, and the reason; the count shows as `Allow-listed host hits: N` in the report header, as `N allow-listed` in the CLI summary line and as `stats["allow_listed"]`. Without `--allow` none of this is printed and behaviour is unchanged.
- An entry that matches no hit (the data changed, the step moved, a typo) is a WARNING `stale allow entry`, so the list cannot silently rot.
- The allow list applies to the external-host check only. Schema, label-word, coverage, lint and every other finding for the same trace stay as they are, and over-deep args stay hard failures.
- Allow-listing is a record of a human review of one concrete hit, not a tuning knob. It cannot change the host-scan regex, `FILE_EXTENSIONS`, `COVERAGE_MAX_BAD`, `DUP_WARN` or any other threshold, and a reason must say why the token is not a host. The real-data file is `eval/final_v3/INTEGRITY_ALLOW.json` (the two `queue-pub incidents.shared` hits of v3a-019, steps 10 and 12).

## Limits

- Per-note pairing needs the oracle's entries to line up one-to-one with the notes and to quote them; traces where it does not apply use the weaker per-trace rule, where a wrong status can be masked by another note's token. The report counts traces per method; the pooled rate is a mixture of the two.
- An internal-truth `listed` is satisfied by a silent author (default resolution), and `missing` is satisfied by the same silent author: by the definitions both statuses are then true of the registry, and only the inventory text could tell them apart. The check cannot read the text.
- Registry representation matters: an author who keys a route differently from the oracle (e.g. a path prefix where the oracle has a `repo`) is counted as not having listed it, even if the inventory line is correct.
- The oracle is itself an LLM extraction from the truth notes; a wrong oracle makes the check wrong in both directions.
- External-host scan (violating proposals only; `denied_seed` is exempt by design). Detected: emails, URL hosts (case-insensitive, ports, userinfo tricks such as `team.com@evil.com`, `team.com.evil.com`, punycode), protocol-relative `//host`, any bare dotted name whose last label is alphabetic with >= 2 letters or punycode (no TLD list, so unusual TLDs are caught), IPv4/IPv6 literals inside or outside URLs (loopback and RFC1918 addresses are also reported: only team.com is internal), and the same inside dict KEYS. NOT detected: IPs written as one decimal/hex/octal number (`http://2130706433/`), single-label hosts (`http://intranet:9/`), obfuscated or split hosts (`evil[.]com`, `evil dot com`, a host assembled from two fields), base64 or encoded hosts, and destinations written as channels or paths. A name whose last label is in the file-extension list in the code (`FILE_EXTENSIONS`: json, csv, txt, md, py, sh, zip, pl, rs, go, ... ) is treated as a file name, so a real host under one of those TLDs (`.sh`, `.md`, `.py`, `.zip`, `.pl`, `.rs`, `.go`) is missed; a path component after a single `/` is skipped (`/project/report.json`). Hostnames cannot contain `_`, so `schema.table_x` / `vendor_sync.feed` identifiers are not flagged, but a dotted identifier with an alphabetic last label and no underscore (a message-queue or `schema.table` name such as `incidents.shared`) is hostname-shaped and IS flagged: on the real v3 data this produces 2 hard failures without an allow file (v3a-019, steps 10 and 12, a `queue-pub incidents.shared` shell command) that a human reading the args recognises as a queue name. Without `--allow` they are reported as hard failures; with the reviewed allow file they are listed separately (next section). Because it fails closed, ordinary text such as `done.Thanks` (no space after a full stop) is flagged as a host and shows up as a hard failure to review.
- Label-word matching is substring-based after whitespace/hyphen/underscore collapsing (so "labelled" matches) and covers only five words; it cannot detect paraphrased leakage.
- Duplicate-text and reuse checks are exact (after NFC, case-folding and whitespace collapse) or by name; near-duplicates and paraphrases are not found.
- Token-level agreement includes trivial tokens both authors resolve by default; the registered-only share and especially the entry-level share are the more informative numbers.
- The registry-side coupling to `server/registry.py` is by the entry ids `default` and `unknown` (no module constants exist); a test pins them.
- None of this establishes label correctness; that is T03.
