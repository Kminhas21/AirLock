# A1 ws access control (bug B3)

## What was built
`server/auth.py`: `check_ws_access(origin, token, env=os.environ) -> AccessResult(allowed, reason)`.
Pure, no FastAPI imports. Reasons: `open` (no token configured), `ok` (token matched), `bad_token`, `bad_origin`.

## Decisions
- Origin is checked before token, so a hostile page learns nothing about token validity.
- Origin `None` => allowed (non-browser client). Any present value, including `""` and `"null"`, must be in the allow-list.
- Origin match is exact string (no trailing-slash/case normalisation): browsers send a canonical origin, and fuzzy matching widens the attack surface.
- `SENTINEL_ALLOWED_ORIGINS`: split on commas, strip whitespace, drop empties. If nothing remains (unset/blank) the defaults apply, never an empty allow-list that would silently lock everyone out, and never the empty string as an allowed origin.
- `SENTINEL_WS_TOKEN` set to "" is treated as unset (a blank env var in a shell/compose file is usually an accident, and matching "" against a missing token would be an auth bypass risk otherwise handled by the empty check).
- Token compare uses `hmac.compare_digest` on UTF-8 bytes (str compare raises TypeError on non-ASCII). A missing token is compared as `b""`, so the path is uniform.
- No logging; the spec's open-mode WARNING is left to the caller, who can act on `reason == "open"`.
- `env` default is bound at definition to `os.environ` (a live mapping); tests always pass a dict.

## Rejected
- Returning on length mismatch early (leaks length; compare_digest handles it).
- Reading env at import time (would defeat testability and late configuration).

## Residual risk
- Token travels in the query string (`?token=`), so it may appear in proxy/access logs; use TLS and rotate.
- Origin is client-asserted for non-browsers; token is the real control. Open mode (no token) is dev-only.
- Not yet wired into `main.py` (integration step).
